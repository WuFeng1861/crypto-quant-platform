## 一、用户原始需求描述

用户需要对回测系统新增一个功能：**批量回测模式**

### 核心需求点：
1. **不传入 pairId**，系统自动获取所有交易对
2. **批量执行回测**：将所有交易对进行回测
3. **详细进度跟踪**：能够实时跟踪每个交易对的回测进度
4. **任务控制功能**：支持随时关闭、暂停、继续、重新执行

## 三、需求澄清与确认

### 3.1 已确认的问题

| 问题 | 用户答复 | 说明 |
|------|----------|------|
| 交易对筛选方式 | 需要多种方式 | 支持全部交易对或指定交易对列表 |
| 批量执行方式 | 串行执行 | 按顺序逐个执行，资源占用较低 |
| 结果展示需求 | 两者都要 | 汇总报告 + 详细列表 |

### 3.2 待确认问题

**[待确认]** 批量回测任务的数据存储方式：
- 方案A：每个交易对生成独立的 backtest_result 记录
- 方案B：创建一个批量任务记录，关联多个子任务

**[待确认]** 暂停功能的实现方式：
- 方案A：优雅暂停（等待当前交易对回测完成后暂停）
- 方案B：强制暂停（立即中断当前回测）

**[待确认]** 重新执行的范围：
- 仅重新执行失败的任务？
- 还是可以选择性重新执行任意任务？

## 四、需求分析

### 4.1 功能需求

#### FR-001: 批量回测任务创建
- 支持不传入 pairId，系统自动获取所有交易对
- 支持传入指定交易对列表
- 支持按条件筛选交易对（交易所、币种类型等）

#### FR-002: 批量回测执行
- 串行执行每个交易对的回测
- 支持配置并发数（未来扩展）
- 每个交易对回测独立记录结果

#### FR-003: 进度跟踪
- 实时显示当前执行进度（已完成/总数）
- 显示每个交易对的执行状态
- 显示预估剩余时间
- 支持查询批量任务的总体状态

#### FR-004: 任务控制
- **关闭**：终止整个批量任务
- **暂停**：暂停执行（等待当前完成后暂停）
- **继续**：从暂停处继续执行
- **重新执行**：重新执行失败或指定的任务

#### FR-005: 结果展示
- 汇总报告：整体统计（平均收益率、胜率等）
- 详细列表：每个交易对的详细回测结果
- 支持导出结果

### 4.2 非功能需求

| 需求项 | 要求 |
|--------|------|
| 性能 | 串行执行避免资源过载 |
| 可靠性 | 支持断点续传，失败可重试 |
| 可扩展性 | 预留并行执行扩展能力 |
| 用户体验 | 实时进度反馈，操作响应及时 |

### 4.3 约束条件

1. 基于现有 NestJS + TypeORM + Redis 架构
2. 复用现有回测计算逻辑
3. 不破坏现有单交易对回测功能
4. 数据库结构变更需兼容现有数据

## 五、风险识别

| 风险点 | 风险等级 | 应对措施 |
|--------|----------|----------|
| 批量任务执行时间过长 | 中 | 支持暂停/继续，避免重复执行 |
| 内存占用过高 | 中 | 串行执行，及时释放资源 |
| 数据库写入压力过大 | 低 | 批量写入优化，使用事务 |
| 任务状态不一致 | 高 | 完善状态机，增加校验机制 |

## 六、假设与依赖

### 6.1 假设
1. 交易对数量在可管理范围内（<1000个）
2. 用户可以接受串行执行的时间成本
3. 系统重启后需要恢复进行中的批量任务

### 6.2 依赖
1. 依赖现有的 trading_pairs 表获取交易对列表
2. 依赖现有的回测计算逻辑
3. 依赖 Redis 进行任务状态缓存
