## 一、需求变更摘要

### 1.1 核心变更
1. **交易对数量上限**: 从 500 提升至 **10000**
2. **新增回测队列系统**: 所有回测任务统一进入队列，串行执行
3. **新增队列管理 API**: 查询队列状态、查看等待任务、取消队列任务

### 1.2 变更原因
- 用户数据库有近 8000 个交易对，500 限制无法满足"自动获取所有交易对"的需求
- 串行执行 + 队列机制可避免系统资源压力

## 二、测试用例更新

### 2.1 需要修改的测试用例

#### TC-001: 创建批量任务-全部交易对
**原预期**:
- 不传 pairIds，自动获取所有交易对
- 预期返回 201，totalPairs > 0

**新预期**:
- 不传 pairIds，自动获取所有交易对（最多 10000 个）
- 预期返回 201，totalPairs = 实际交易对数量（如 8000）

#### TC-009: 交易对数量上限
**原预期**:
- 传入 501 个 pairIds
- 返回 400，错误码 `PAIR_LIMIT_EXCEEDED`
- 错误信息包含 "500"

**新预期**:
- 传入 10001 个 pairIds
- 返回 400，错误码 `PAIR_LIMIT_EXCEEDED`
- 错误信息包含 "10000"

#### TC-009a: 交易对数量边界
**原预期**:
- 传入 500 个 pairIds
- 返回 201，totalPairs = 500

**新预期**:
- 传入 10000 个 pairIds
- 返回 201，totalPairs = 10000

### 2.2 新增测试用例

#### TC-100: 队列状态查询
- **前置条件**: 有回测任务在队列中或正在执行
- **输入**: GET /backtest/queue/status
- **预期结果**:
  - 返回 200
  - 包含 isProcessing, currentTask, queueLength, maxQueueLength
  - currentTask 包含 id, type, progress, startedAt

#### TC-101: 队列列表查询
- **前置条件**: 有多个任务在队列中
- **输入**: GET /backtest/queue?page=1&limit=20
- **预期结果**:
  - 返回 200
  - 返回 items 数组，每个包含 taskId, type, strategyId, status, queuedAt
  - 包含 pagination 信息

#### TC-102: 队列满时创建任务
- **前置条件**: 队列中已有 100 个任务
- **输入**: POST /backtest/batch (或 POST /backtest)
- **预期结果**:
  - 返回 429
  - 错误码 `QUEUE_FULL`
  - 错误信息: "回测队列已满，请稍后重试"

#### TC-103: 取消队列中的任务
- **前置条件**: 任务在队列中，状态为 queued
- **输入**: DELETE /backtest/queue/:taskId
- **预期结果**:
  - 返回 200
  - 任务从队列中移除
  - 任务状态变为 cancelled

#### TC-104: 取消已开始任务失败
- **前置条件**: 任务已开始执行（状态为 processing）
- **输入**: DELETE /backtest/queue/:taskId
- **预期结果**:
  - 返回 400
  - 错误码 `TASK_ALREADY_STARTED`
  - 错误信息提示使用取消任务接口

#### TC-105: 串行执行验证
- **前置条件**: 创建两个批量任务
- **输入**: 依次创建任务 A 和任务 B
- **执行步骤**:
  1. 创建任务 A（10 个交易对）
  2. 立即创建任务 B（10 个交易对）
  3. 观察队列状态和任务执行
- **预期结果**:
  - 任务 A 进入 processing 状态
  - 任务 B 在队列中，状态为 queued
  - 任务 A 完成后，任务 B 才开始执行

#### TC-106: 队列顺序验证
- **前置条件**: 按顺序创建多个任务
- **输入**: 创建任务 A、B、C
- **预期结果**:
  - 队列中顺序为 A、B、C
  - 执行顺序为 A → B → C

## 三、HTTP 测试脚本更新

### 3.1 配置更新
- API 基础 URL: `http://localhost:3099`

### 3.2 新增测试脚本内容

```javascript
// 队列状态查询测试
describe('GET /backtest/queue/status - 队列状态查询', () => {
  it('TC-100: 查询队列状态', async () => {
    const response = await api.get('/backtest/queue/status');
    
    assert.strictEqual(response.status, 200);
    assert.strictEqual(response.data.success, true);
    assert.ok(typeof response.data.data.isProcessing === 'boolean');
    assert.ok(typeof response.data.data.queueLength === 'number');
    assert.ok(response.data.data.maxQueueLength === 100);
  });
});

// 队列满测试
describe('队列满处理', () => {
  it('TC-102: 队列满时创建任务', async function() {
    this.timeout(60000);
    
    // 尝试填满队列（假设队列当前为空）
    const promises = [];
    for (let i = 0; i < 105; i++) {
      promises.push(
        api.post('/backtest/batch', { ...TEST_DATA, pairIds: [1] })
          .catch(err => err.response)
      );
    }
    
    const results = await Promise.all(promises);
    
    // 检查是否有 QUEUE_FULL 错误
    const queueFullErrors = results.filter(
      r => r.status === 429 && r.data.error.code === 'QUEUE_FULL'
    );
    
    assert.ok(queueFullErrors.length > 0, '应该有队列满的错误');
  });
});
```

## 四、测试数据准备

### 4.1 需要的数据
1. **大量交易对**: 准备 10000+ 交易对用于边界测试
2. **策略数据**: 至少 1 个有效策略

## 六、测试策略更新

### 6.1 测试重点
1. **队列功能**: 确保所有回测任务都进入队列
2. **串行执行**: 验证任务按顺序执行，不并发
3. **边界测试**: 10000 交易对、100 队列长度
4. **错误处理**: QUEUE_FULL、TASK_ALREADY_STARTED

### 6.2 测试顺序建议
1. 先测试单任务功能（创建、查询、控制）
2. 再测试队列功能（状态、列表、取消）
3. 最后测试边界条件（10000 交易对、队列满）
